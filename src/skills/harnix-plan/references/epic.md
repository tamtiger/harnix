# Epics

Use when an initiative, refactor or chain of work has two or more tasks, or the user asks to link work to a larger initiative. An epic is mandatory then; never invent an `epicId` for a single standalone task.

1. IDs: English only (`--init` takes `--slug <english-kebab-case>`; titles, goals and criteria stay Vietnamese with accents): `YYYYMMDD-HHMMSS-<name>` from `clock.idPrefix`, for the epic and every task (task IDs must match `^\d{8}-\d{6}-[a-z0-9]+(?:-[a-z0-9]+)*$`). Members run in ID order: `harnix epic` lists them and picks the next task by ID, and `--save` rejects members whose IDs do not increase in the order you declare them. Give each member a later idPrefix than the one before it (add one second per member), the first task first.
2. Create the epic and all member tasks up front in one `--save` envelope: `epic` (`id`, `title`, `goal`, optional `nonGoals`, plus `generator`, `schemaVersion: 1`, `createdAt`, `updatedAt`), the first task with `epicId`, and every other member in `epicMembers` (schema v3, status `planning`, same `epicId`).
3. `.harnix/epics/<epic-id>/epic.json` is task-owned data; `<epic-id>/epic.md` is derived and regenerated on save (a flat `.harnix/epics/<epic-id>.json` is migrated). The folder may also hold task-owned initiative notes such as `research.md` (or `research/`) and `spec.md`, never overwritten by the CLI and linked from `epic.md` under `## Supporting Artifacts`. Never hand-edit `epic.json` or `epic.md`.
4. Inspect with `harnix epic` (list) or `harnix epic <epic-id>` (members and the next task). When the epic is created or ready, stop for user review (`nextStage: await`): present the member sequence and scope to the user and wait for approval before running the first task. When a member finishes, report the epic's progress and recommend the next member.
5. The flag transports (`--set-check`, `--add-criterion`, `--set-criterion`, `--set-paths`, `--set-title`, `--set-goal`, `--add-decision`, `--add-risk`, `--remove-decision`, `--remove-criterion`, `--remove-risk`, `--batch`) and `--inspect` act on the active task unless you add `--task <task-id>` to edit or read another unfinished member (for example a `planning` epic member) without touching the active pointer, under the same rules (`--reason` after planning, immutability, the workflow lock); `--cancel --task <task-id>` cancels another unfinished member; `--transition`, `--finish`, `--run-check` and `--evidence` act only on the active task, and a finished task refuses `--task`.
6. A later task of the same initiative is created with `harnix workflow --init ... --epic <epic-id>`, never with `--follow-up` alone (`--follow-up` only records `followUpOf` and inherits the parent's epic and paths; a `notice:` on stderr says when the parent has none). An epic is never attached retroactively to an existing task, so decide it at creation. To add a member while another task is active, create it with `--init --epic <epic-id> --no-activate`, which leaves `.active` where it is.
7. Members created up front carry draft criteria and checks: before marking one `ready`, check them against the current code, tests and contracts (earlier members may have moved or deleted files) and adjust them before they freeze.

## Grouping members

Each member pays a full lifecycle (plan, ready, verify, finish, a dev version bump, a suite run), so size members first. A member is one independently verifiable change, not one list item: problems in the same module or files, of the same kind (for example only diagnostic messages) and sharing one focused check go in one member with several criteria. Split only when the contract, risk or order differs (a frozen-contract change, a security-sensitive path, a separate merge). Aim for 3 to 6 members and look for a merge before creating more; members editing the same file near the 300-code-line cap go together or in a declared order. Members never run can be merged by moving their criteria into a survivor (`--task <id> --batch`) and cancelling the rest.

Review an epic once (`harnix-review`, whole epic diff) after its last member is implemented.

## Run order

Members run in ID order unless the epic declares an optional `order` (task ids, distinct, all members of the epic). `harnix workflow --epic-order <epic-id> <task-id>...` sets it (no task ids clears it) and rewrites only the epic record and its page, never a `task.json`. `harnix epic <epic-id>` lists the ordered members first in that order and the rest by ascending ID, and `nextTask` is the first unfinished member in that sequence; an epic without `order` behaves as before.

Git branching, task switching and concurrent members in worktrees (the Multi-Agent section): `harnix skill harnix-plan --reference epic-git`.
